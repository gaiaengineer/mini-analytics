# Architecture & data flow

## The business behind the data

The data describes a **digital book marketplace**. An author publishes a book and issues some number of **tokens**: each token is one numbered digital copy of that book. In this codebase "token" and "copy" mean the same thing.

### Supply types (not captured in the CSVs)

- **Unlimited supply.** The author can keep issuing new copies. There's no "sell-out", so per-book purchase rates on these books are directional at best: a low rate isn't a failure.
- **Limited supply.** A fixed maximum of copies can ever exist. Once they're all sold, no more are issued.
- For **limited** books, the author chooses at publish time whether to **allow resale** of copies already sold:
  - **Resale enabled** → a secondary market exists, and `flow_type = 'purchase_from_resale'` rows can appear.
  - **Resale disabled** → once every copy is sold, there is no secondary market for that book.

**None of the CSVs contains a `book_supply_type` or `resale_enabled` flag.** Metrics that depend on that distinction (per-book purchase rate, resale share, issuance–purchase gap) carry a disclaimer on the dashboard, because "is this book underperforming" can't be computed rigorously from this data.

### A token is reserved *before* the payment clears

The lifecycle of a sale:

1. A row appears in `token_purchases` with `state = 'initiated'` (sometimes `'prepared'`). **The copy is already reserved for the buyer at this point.**
2. The buyer is sent to a third-party payment provider to pay.
3. On success, `state` flips to `'purchased'` and `flow_type` is set.
4. On failure it becomes `'failed'`, or it may stay at `'initiated'` / `'prepared'` if something went wrong asynchronously.

**Consequence:** `tokens issued > tokens sold` can be caused by **any** of:

- The buyer closed the browser before paying.
- The payment provider declined the transaction (card declined, fraud check, etc.).
- The marketplace failed to record a successful payment.
- The book is unlimited-supply and simply hasn't sold its current copies yet.

The data has no `payment_result` signal, so these four causes can't be told apart. The dashboards that show the gap (Token Issuance & Purchases, Token Lifecycle, Conversion Funnel, Primary vs Resale) carry a visible `note` block saying so.

## One-paragraph summary

Raw CSVs land in `data/raw/` (either generated by `scripts/make_demo_data.py` or freshly fetched from S3 — see "Where the CSVs come from" below). A small Python CLI (`mini-analytics`) loads them into an in-memory DuckDB database as **views** (not copies), registers three **model views** on top that normalise types and names, then runs the SQL in each dashboard YAML to produce a static HTML page plus one CSV per chart. Nothing is persisted between runs — re-running `ingest` or `build` is cheap and idempotent.

## Where the CSVs come from

The four CSVs in `data/raw/` are not the source of truth — they're a local cache of the latest export the upstream warehouse job wrote to S3.

- **Bucket:** `s3://your-export-bucket/`
- **One prefix per logical table:**
  - `exports/authors/`, `exports/books/`, `exports/tokens/`, `exports/token_purchases/` — plain `*.csv`, refreshed every 6 hours, ~10 days of history.
  - `imports/ga_events/` — Google Analytics events, gzipped daily exports (`*.csv.gz`).
- File naming under each prefix is timestamp-based (`YYYYMMDD-HHMMSS.csv` or `YYYYMMDD_YYYYMMDD__YYYYMMDD-HHMMSS.csv.gz` for `ga_events`).
- `mini-analytics fetch` lists each prefix, picks the most-recently-modified object whose key ends in `.csv` **or** `.csv.gz`, and downloads it as `data/raw/<table>.<ext>` preserving the original extension. Tied `LastModified`s break by descending key (lexicographic) — file naming is timestamp-based so this matches reality.
- `mini-analytics build --refresh` does a `fetch` first, then a normal build. The bare `build` doesn't touch S3, so dashboard iteration stays fast.
- DuckDB's `read_csv_auto` reads gzipped CSVs directly; there's no separate decompression step.

**Credentials.** Read from the standard AWS chain — env vars (`AWS_ACCESS_KEY_ID`, `AWS_SECRET_ACCESS_KEY`, `AWS_DEFAULT_REGION`), then `~/.aws/credentials` profile (configured via `aws configure --profile <name>`), then any IAM role available at runtime. **Never** in `sources.yml`, never in the repo.

The `[s3]` block in `sources.yml` only carries the bucket / region / prefixes / profile name, never the secret material:

```yaml
s3:
  bucket: your-export-bucket
  region: us-east-1
  profile: mini-analytics      # name of the local AWS profile to use
  download_to: data/raw
  prefixes:
    authors:         exports/authors/
    books:           exports/books/
    tokens:          exports/tokens/
    token_purchases: exports/token_purchases/
    ga_events:       imports/ga_events/        # gzipped daily GA event exports
```

For a scheduled rebuild (e.g. GitHub Actions), the workflow can assume an IAM role via OIDC instead of using a long-lived access key — the `[s3]` block stays the same, only the `profile:` line drops.

## The data we have

Four CSV files, in a clear parent/child chain:

```
authors
  └── books (author_id → authors.id)
        └── tokens (book_id → books.id)
              └── token_purchases (token_id → tokens.id)
```

The business model, as expressed in this data: authors publish books; each book has a fixed pool of **tokens** (think "numbered editions" or "ownership units"); each token can be bought from the author (primary market) or resold (secondary market).

### Raw source tables — exactly as they appear in the CSVs

| Table | Columns | Notes |
|---|---|---|
| `authors` | `id`, `name` | `name` can be blank: some accounts never set a display name. |
| `books` | `id`, `author_id`, `title` | Every book belongs to exactly one author. |
| `tokens` | `id`, `book_id` | One row per issued copy. |
| `token_purchases` | `id`, `token_id`, `state`, `price_cents`, `flow_type`, `purchase_date`, `created_at` | One row per attempted or completed purchase of a copy. |
| `ga_events` | `event_date`, `event_name`, `user_pseudo_id`, `session_id`, page, device, geo and traffic-source columns | Google Analytics export, one gzipped CSV per day. |

### Key conventions you'll see everywhere

- **`state`** is `'purchased'` (the sale went through), or `'initiated'`, `'prepared'` or `'failed'` (started but didn't complete). Only `'purchased'` rows count toward GMV.
- **`flow_type`** is `'purchase_from_author'` (primary market), `'purchase_from_resale'` (secondary market), or `'unknown'` (a data-quality bucket — see the Token Lifecycle and Primary vs Resale dashboards).
- **`price_cents`** is integer US cents. Every dashboard divides by 100 at the moment of display. The raw view never does — money is always stored as cents to avoid float rounding.
- **`purchase_date`** is often `NULL` on `prepared` rows, and rarely `NULL` on a handful of `purchased` rows. Every time-series query filters out `purchase_date IS NULL`.
- **`created_at`** is always set; it's when the row was first written. Useful for anything that cares about "was this attempted" vs "when did the sale clear".

## How the data moves

```
┌────────────┐     ┌───────────────────┐     ┌──────────────────┐     ┌──────────────┐
│ CSV files  │ ──▶ │ DuckDB source     │ ──▶ │ Model views      │ ──▶ │ Dashboards   │
│ data/raw/  │     │ views (1:1 copies)│     │ (normalised, JOINs)│   │ (YAML + SQL) │
└────────────┘     └───────────────────┘     └──────────────────┘     └──────┬───────┘
                                                                              │
                                                                              ▼
                                                                       ┌───────────────┐
                                                                       │ build/        │
                                                                       │ HTML + CSVs   │
                                                                       └───────────────┘
```

All tables in DuckDB are **views**, not copied tables. Running `ingest` creates views that point at the CSVs with explicit types; the files are re-read on every query. For ~3k total rows this is instant.

### Source views (the loader creates these)

Exact 1:1 image of the CSVs, with types pinned up front so later dashboards don't get surprised by implicit casts:

- `authors (id INTEGER, name VARCHAR)`
- `books (id INTEGER, author_id INTEGER, title VARCHAR)`
- `tokens (id INTEGER, book_id INTEGER)`
- `token_purchases (id INTEGER, token_id INTEGER, state VARCHAR, price_cents INTEGER, flow_type VARCHAR, purchase_date TIMESTAMP, created_at TIMESTAMP)`

### Model views (registered after the loader runs)

The **contract** between "raw data" and "dashboards". Every dashboard queries model views, never the raw source views. This way, if the CSV schema changes tomorrow (or we swap CSV for Postgres), only the model views need to be updated — every dashboard keeps working.

**`fct_token_purchase`** — one row per `token_purchases` row, joined up to its book and author.

| Column | Meaning |
|---|---|
| `purchase_id` | Original `token_purchases.id`. |
| `token_id`, `book_id`, `author_id` | Full parent chain. |
| `book_title`, `author_name` | Denormalised for convenience. |
| `state` | `'purchased'` or `'prepared'`. |
| `is_purchased` | Boolean = `state = 'purchased'`. Use this instead of re-checking state. |
| `price_cents` | Integer cents. |
| `flow_type` | Normalised — any NULL in the source becomes `'unknown'`. |
| `purchase_date` | Cast to `DATE` (day precision). |
| `created_at` | Original timestamp. |

**`dim_book`** — one row per book, with inventory and revenue aggregates already rolled up.

| Column | Meaning |
|---|---|
| `id`, `author_id`, `title` | From `books`. |
| `token_count` | How many tokens were issued for this book. |
| `tokens_sold` | How many distinct tokens have at least one `purchased` purchase row. |
| `gmv_cents` | Sum of `price_cents` on this book's purchased tokens. |

**`dim_author`** — one row per author, rolled up further.

| Column | Meaning |
|---|---|
| `id`, `name` | From `authors`. |
| `book_count` | Books where `author_id` matches. |
| `token_count` | Sum of `dim_book.token_count` for the author's books. |
| `tokens_sold` | Sum of `dim_book.tokens_sold`. |
| `gmv_cents` | Sum of `dim_book.gmv_cents`. |

> **Rule of thumb:** raw source views are fine for audit queries and ad-hoc exploration. Dashboards should read from the model views. Every dashboard YAML in this repo already follows this.

## Output structure

`mini-analytics build` produces exactly this tree under `build/`:

```
build/
├── index.html                               # Landing page — lists every dashboard
└── <dashboard_id>/
    ├── index.html                           # The dashboard page
    └── exports/
        ├── <block_id>.csv                   # One CSV per block (including KPIs)
        ├── ...
```

- `build/` contains no server code and no database — it's 100% static files.
- Every chart on every dashboard has a **Download CSV** button that points at the corresponding `.csv`.
- Plotly (the chart library) is loaded from a public CDN. If the deployment ever needs to be air-gapped, one line in `rendering/renderer.py` flips it to bundle Plotly locally.

## Why it's built this way

| Choice | Why |
|---|---|
| **DuckDB** as the engine | Reads CSVs natively; later swaps to Postgres/MySQL via its extensions with zero dashboard changes. |
| **Views, not tables** | Re-ingest is free; nothing to keep in sync. Swapping the source means swapping a view definition. |
| **Model views as a contract** | Shields dashboards from raw-column drift. Dashboards never know where data came from. |
| **YAML dashboards** | Analyst-editable. Reviewable as diffs. An LLM can propose new dashboards by writing one. |
| **Static HTML output** | No server to run. Refreshing = re-running `build`. Fits any hosting, any auth story. |
| **Plotly + Jinja + Pandas** | All mature, all pip-installable. No custom JS. |
